## Three kinds of expectations

1. **Preserve:** public export names/value kinds, ordered legacy projection,
   UI navigation callbacks, copied-story parity, existing golden snapshots.
2. **Record truth:** independently known values and original addresses from
   genuine Flow 10/HCI 3 recordings, checked separately in the Node 22 pilot.
3. **Diagnostic observations:** explicitly labelled old wrong or incomplete
   answers in `corrections.json`. These are not correctness oracles. A later
   correction changes the corresponding observation under an owning-layer
   review; it must not update the record truth to match an old bug.

For example, the real fork snapshot ends with both A's `y = 2` and B's `x = 9`.
The old tree-based view instead shows Join with Seed's `x = 1`. R1 asserts both
facts and their disagreement. R2 similarly distinguishes A's own row 1 from the
old historical label pointing at empty repeat row 3. R4 retains the historical
Foottrace 1.0.0 defect observation in the ledger, while its regression now
requires the corrected answer first adopted from the public 1.0.1 reader.
The current M4 branch uses public 1.0.3, including its saved-tree and saved-path
validation fixes. The producer fixtures and their version metadata remain
unchanged; no Lens workaround duplicates those owning-library rules.

### Boundaries still requiring later evidence

This corpus does not assert that handcrafted legacy inputs are a complete list
of supported historical formats. M2 must select an explicit format policy and
capture any additional real older formats before claiming their support.

The real HCI recording includes committed and pending transitions, not a complete
rejected/rolled-back interaction ledger. The record viewer must not claim that
those missing actions are committed state. Additional producer scenarios belong
with a separately reviewed HCI adapter/ledger contract.

The current composite root does not implement the proposed lazy graph-loading
boundary. There is no honest current graph-load-failure baseline to freeze; the
future loading implementation needs its own success/failure/remount tests.
Stage-level reads are not per-write proof, and the old presence of any reads
must not become a claim of complete capture. R3 and the existing pilot's visible
unknown-read qualification preserve that distinction for the later adapter.

## Run

Current Node 22/24 suite (M3 state, M4 stage causality and M5 variable queries delegate to Foottrace):

```sh
npm run build
npm test
```

Node 22 or newer only, including the four new canonical-reader cases:

```sh
npm run test:record-pilot
```

Run the unchanged `publint` and `attw --pack` gates as in CI. The fixture corpus,
diagnostic ledger and test helpers are outside the published `dist` allowlist.
Do not regenerate any input/output baseline to make a migration pass.
